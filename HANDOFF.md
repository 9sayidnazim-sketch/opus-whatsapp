## 2. Browser Web Push Notifications Architecture
Engineered per the user request for native browser push notification capability:
- **Service Worker (`public/sw.js`):**
  - Handles `push` events with JSON/text payload parsing, custom icons (`/favicon.svg`), vibration pattern `[100, 50, 100]`, and action buttons ("Open Ledger", "Dismiss").
  - Handles `notificationclick` events with multi-window routing and tab focusing.
- **Notification Utility Module (`src/utils/notifications.js`):**
  - `isNotificationSupported()`: Browser feature detection.
  - `getNotificationPermission()`: State detection (`default` | `granted` | `denied`).
  - `registerServiceWorker()`: Auto-registers `/sw.js` with root scope.
  - `requestNotificationPermission()`: Interactive prompt handler.
  - `showBrowserNotification()`: Dual-path fallback supporting Service Worker notifications with Window Notification API fallback.
  - `sendTestPushNotification()`: Interactive test trigger with custom badge.
  - `checkAndTriggerDueAlerts()`: Automated evaluation engine that triggers alerts for:
    1. **Upcoming Bills:** Pending bills due in $\le 3$ days (or custom threshold).
    2. **Budget Threshold Warnings:** Budgets that have reached or exceeded the set threshold ($\ge 80\%$).
- **UI Integration:**
  - **Dashboard (`src/pages/Dashboard.jsx`):** Automatically evaluates due bills and budget limits on load; displays an interactive 1-click "Enable Alerts" card in `NotificationsBanner.jsx` when permission is unprompted.
  - **Settings (`src/pages/Settings.jsx`):** Dedicated "Browser Push Notifications" card with live permission status pill, one-click enablement, and a "Send Test Push" button.
  - **Header & Mobile Header (`src/Layout.jsx`):** Quick notification bell button with active status indicator.

## 4. SimpleWebAuthn Biometrics Architecture
Engineered per the user request using `@simplewebauthn/browser` and `@simplewebauthn/server`:
- **Hardware Integration:**
  - Automatic detection of biometric support via `checkBiometricsSupport()` (`browserSupportsWebAuthn` and `platformAuthenticatorIsAvailable`).
  - Native hardware enclave integration for Face ID, Touch ID, Windows Hello, and Android Biometrics.
- **Registration Flow:**
  - `POST /api/webauthn/registration-options`: Generates challenge, RP details (`Fuloozi Household Ledger`), and cryptographic public key parameters via `@simplewebauthn/server`.
  - Client prompts native Touch ID / Face ID sheet via `startRegistration({ optionsJSON })`.
  - `POST /api/webauthn/verify-registration`: Validates attestation response and stores credential ID, public key, counter, and friendly device name.
- **Authentication Flow:**
  - One-tap "Sign in with Face ID / Touch ID" on the Sign In screen.
  - Native biometric prompt signs the server challenge.
  - On verification, creates authenticated session and opens ledger instantly without typing.
  - Seamless fallback to 4-digit MPIN always available.
- **Settings Management:**
  - Device Passkeys card in Settings with enrollment status, hardware badges, and credential deletion.

## 8. WhatsApp webhook and dev API hardening (2026-11-15, Claude Code)
Branch `claude/agitated-jennings-bac7e5` (worktree `.claude/worktrees/agitated-jennings-bac7e5`), on top of main `aaa3e26`. Not merged yet.

**Done**
1. **Webhook signatures fail closed** (`api/whatsapp.js`, commit `3666412`). The webhook now uses Web Request handlers (named `GET`/`POST` exports). Vercel calls these without its JSON body parser, so the HMAC is checked over the exact bytes received. Kapso documents the header as `X-Webhook-Signature`: the hex HMAC-SHA256 of the raw body, keyed with the webhook's `secret_key`, no `sha256=` prefix, for both Kapso and Meta webhook kinds. A missing, malformed or wrong signature gets 401. Without `KAPSO_WEBHOOK_SECRET`, every POST gets 503. The comparison is `timingSafeEqual` after a length check.
2. **Reflected XSS closed** (same commit). The `hub.challenge` echo went through Vercel's `res.send`, which serves strings as `text/html`, so a crafted link ran script on the app origin. It now goes out as `text/plain` with `nosniff`.
3. **Dev endpoints that send WhatsApp messages stay on this computer** (`server/localRequest.js`, `vite.config.js`, commit `ba22a82`). `/api/kapso/send` and `/api/kapso/simulate` now need all of: a loopback peer, a loopback Host, no proxy or tunnel headers, and a same-origin Origin when one is sent. Anything else gets 403. This also blocks other sites open in the browser and DNS rebinding, which mattered because plugin middleware runs before Vite's own CORS and host checks.
4. **The dev `/api/whatsapp` route runs the production handler.** Before, it processed unsigned events and replied to whatever `sender` they named. Now it checks signatures like production. `.env.local` has no `KAPSO_WEBHOOK_SECRET` today, so it answers 503; use `/api/kapso/simulate` for local testing.
5. The Settings simulator shows the refusal message instead of a success toast.

**Verified**
- `npm test`: 19 node:test cases with `fetch` stubbed. Signed events pass. Unsigned, wrong-secret, tampered, re-serialised and malformed signatures fail. With no secret, POSTs get 503. The challenge comes back as inert text.
- The old handler, called the way Vercel calls it (body already parsed), accepted unsigned and forged events and sent replies.
- Worktree dev server on port 5199, with the Kapso credentials blanked so nothing could reach WhatsApp. From this computer, send and simulate went through. Via the LAN IP, a foreign Host, a cross-site Origin or `X-Forwarded-For`, they got 403. The dev webhook rejected unsigned and forged events with 401 and accepted a signed one with 200.
- In the in-app browser, the Settings simulator works at `localhost:5199`. Opened via `192.168.0.157:5199`, it shows the refusal.
